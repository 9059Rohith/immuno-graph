# Deterministic Algorithm Specification

## 1. Contract

All algorithms in this document are pure functions. Given the same canonical input, configuration profile, and ordered evidence snapshot, they must return canonical JSON-equivalent results.

Numerical rules:

- calculations use JavaScript `number`;
- persisted values retain at least six decimal places;
- UI rounding is presentation-only;
- comparisons use unrounded values;
- input arrays are explicitly sorted before aggregation;
- `NaN`, positive infinity, and negative infinity are invalid.

## 2. FASTA parsing and normalization

### Input

One UTF-8 FASTA record, maximum default length 10,000 residues and maximum upload size 1 MiB.

### Procedure

```text
normalize line endings to LF
remove UTF-8 BOM
require exactly one header beginning with ">"
join non-header lines
remove ASCII whitespace
uppercase using locale-independent rules
strip one terminal "*" if present
reject any internal "*"
validate each character against configured protein alphabet
calculate SHA-256 over the normalized sequence
```

Default strict alphabet: `ACDEFGHIKLMNPQRSTVWY`. Ambiguous residues `B`, `J`, `O`, `U`, `X`, and `Z` are rejected in the MVP unless an approved profile explicitly allows them.

If a sequence of at least 30 characters contains only `A`, `C`, `G`, `T`, `U`, or `N`, return `SEQUENCE_APPEARS_NUCLEOTIDE`.

### Complexity

Time `O(n)`, space `O(n)`.

## 3. Candidate peptide generation

### MHC-I

Default lengths: 8, 9, 10, 11.

### MHC-II

Default lengths: 13 through 25, configurable to a smaller approved set for live tool limits.

### Pseudocode

```text
for each length L in ascending configured lengths:
  if L > sequence.length: continue
  for start0 from 0 through sequence.length - L:
    peptide = sequence.slice(start0, start0 + L)
    emit {
      start: start0 + 1,
      end: start0 + L,
      length: L,
      peptide,
      candidateType
    }
sort by candidateType, start, length, peptide
```

B-cell prediction is whole-sequence/residue based. B-cell regions are produced by the registered connector and are not generated by the T-cell sliding-window function.

### Complexity

`O(n * k)` time and output space, where `k` is the number of configured lengths.

## 4. Canonical cache key

```text
sha256(canonicalJson({
  sequenceHash,
  connectorId,
  connectorVersion,
  method,
  methodVersion,
  candidateType,
  alleles: sortedAlleles,
  peptideLengths: sortedLengths,
  parameters: recursivelyKeySortedParameters,
  outputSchemaVersion
}))
```

Fallback policy, timestamps, request IDs, and retry count are not part of the scientific cache key. Any scientific parameter is part of the key.

## 5. Score registry and normalization

Every numeric predictor field has a registered profile:

```ts
type NormalizationProfile =
  | { kind: 'IDENTITY'; min: 0; max: 1; direction: 'HIGHER_BETTER' }
  | { kind: 'INVERSE_PERCENTILE'; cap: number }
  | { kind: 'FIXED_MIN_MAX'; min: number; max: number; direction: ScoreDirection }
  | { kind: 'LOGISTIC'; midpoint: number; slope: number; direction: ScoreDirection };
```

Sample-dependent min-max scaling across the current run is forbidden for the primary score because adding candidates would change earlier normalized values.

### Clamp

`clamp01(x) = min(1, max(0, x))`

### Identity

`normalized = clamp01(raw)`

### Inverse percentile

For lower-is-better percentile rank `r` and registered cap `c > 0`:

`normalized = 1 - clamp01(r / c)`

The raw rank remains available. The cap must be stored with the result.

### Fixed min-max

`base = clamp01((raw - min) / (max - min))`

If higher is better, `normalized = base`; otherwise `normalized = 1 - base`.

### Logistic

`base = 1 / (1 + exp(-slope * (raw - midpoint)))`

Invert when lower is better.

Unknown methods or unregistered score fields are not normalized and cannot contribute to ranking.

## 6. Evidence grouping

Comparable T-cell evidence has the same:

- protein hash;
- peptide coordinates and sequence;
- candidate type (`MHCI` or `MHCII`);
- HLA allele;
- prediction target semantics.

B-cell evidence is grouped by overlapping predicted region after coordinate mapping, but is never combined with T-cell binding evidence.

## 7. Consensus and disagreement

For normalized comparable scores `x_i` with registered non-negative reliability weights `w_i`:

```text
weightedMean = sum(w_i * x_i) / sum(w_i)
weightedVariance = sum(w_i * (x_i - weightedMean)^2) / sum(w_i)
agreement = clamp01(1 - 4 * weightedVariance)
```

For values in `[0,1]`, variance is at most `0.25`; therefore the scaled agreement is bounded.

Evidence completeness:

```text
completeness = presentRequiredWeight / configuredRequiredWeight
```

Consensus score:

```text
consensus = weightedMean * (0.70 + 0.30 * agreement) * completeness
```

All component values are persisted. A single observation can yield a mean but not multi-predictor agreement; mark `agreementStatus = INSUFFICIENT_OBSERVATIONS` and route to review unless the profile explicitly permits a single authoritative method.

### Categorical entropy

For displayed support classes with proportions `p_j`:

```text
entropy = -sum(p_j * ln(p_j)) / ln(numberOfNonEmptyClasses)
```

When fewer than two non-empty classes exist, entropy is `0`. Entropy is explanatory and does not replace the numeric agreement formula.

## 8. Duplicate detection

Exact duplicate key:

```text
proteinHash | candidateType | start | end | peptide | allele
```

Group identical keys. Keep the canonical candidate with the lowest UUID lexical order. Merge observation references; record `DUPLICATE_OF` edges and `DUPLICATE-001` rejections for removed records. Identical peptide sequences at different coordinates are distinct positional candidates and must never be collapsed as duplicates.

Time `O(n)` average with a map.

## 9. Overlap detection and pruning

For two intervals `[a1, a2]` and `[b1, b2]`, inclusive:

```text
intersection = max(0, min(a2, b2) - max(a1, b1) + 1)
containmentOverlap = intersection / min(lengthA, lengthB)
```

Candidates are eligible for overlap competition only when they share protein, candidate type, and—where applicable—HLA allele.

Default dominance threshold: `containmentOverlap > 0.80`.

Within an overlap component, sort by:

1. passes all hard constraints;
2. higher preliminary score;
3. higher evidence completeness;
4. higher agreement;
5. shorter peptide;
6. earlier start coordinate;
7. lexical candidate key.

Keep the first. Other candidates become `REJECTED` with rule `BIO-OVERLAP-001` and a link to the retained candidate. The threshold is a versioned profile value, not a hard-coded constant.

## 10. Population coverage

The MVP does not invent an allele-frequency model. Authoritative set-level coverage is obtained from a registered population-coverage connector or an exact fixture that records its source dataset and calculation mode.

Required outputs:

- projected coverage;
- average epitope hits or HLA combinations per person when available;
- PC90 when available;
- population identifier;
- MHC class mode;
- source/method/version.

The ranking input for one T-cell candidate is its singleton projected coverage, calculated independently of any proposed shortlist:

```text
candidateCoverage(c) = coverage({c})
```

`candidateCoverage` is already a unit-interval value and may participate in ranking without creating a dependency on a not-yet-selected shortlist.

After final individual ranking, shortlist optimization uses marginal set coverage. Starting with `S = {}`:

```text
marginalCoverage(c, S) = max(0, coverage(S union {c}) - coverage(S))
```

At each step, choose the eligible unselected candidate by:

1. highest marginal coverage;
2. higher final candidate score;
3. earlier final track rank;
4. lexical candidate key.

Stop at the configured shortlist size or coverage target. Persist each selection step, its gain, and cumulative coverage. If repeated service calls are impractical, the connector may return a documented deterministic batch matrix that produces the same selection inputs. Missing coverage is not replaced by an LLM estimate.

No HLA population-coverage value applies to B-cell candidates.

## 11. Constraint engine

Rules return:

```ts
type RuleOutcome = {
  ruleId: string;
  ruleVersion: string;
  severity: 'HARD' | 'SOFT';
  outcome: 'PASS' | 'WARN' | 'FAIL' | 'NOT_EVALUATED';
  evidenceRefs: string[];
  message: string;
};
```

### Initial rule catalog

| Rule | Default behavior |
|---|---|
| `SEQ-LENGTH-001` | Hard fail if peptide length is invalid for its track. |
| `HLA-SUPPORTED-001` | Hard fail if allele is unsupported by the chosen method. |
| `BINDING-001` | Hard fail when no required binding observation meets the profile threshold. |
| `EVIDENCE-REQUIRED-001` | Hard fail when required evidence is absent after execution. |
| `DISAGREEMENT-001` | Soft warn below agreement 0.60; profile may make it hard. |
| `POPULATION-001` | Soft warn when required singleton coverage evidence is missing or falls below the profile threshold. |
| `DUPLICATE-001` | Hard fail non-canonical exact duplicate. |
| `BIO-OVERLAP-001` | Hard fail dominated overlapping candidate after preliminary scoring. |
| `FIXTURE-PROVENANCE-001` | Soft warn for fixture-backed evidence; affects run quality, not biology. |

Defaults are starting profiles requiring domain review before non-demo use.

Rule evaluation order:

```text
schema/length -> allele support -> required evidence -> binding ->
consensus/disagreement -> singleton population coverage -> duplicate ->
preliminary rank -> overlap dominance -> final rank
```

## 12. Ranking

Rank candidates only within one track and ranking profile.

### MHC-I and MHC-II MVP profile

```text
scoreBeforePenalty =
    w_binding * bindingQuality
  + w_consensus * consensusQuality
  + w_coverage * candidateCoverage
  + w_completeness * completeness

w_binding + w_consensus + w_coverage + w_completeness = 1.0
```

Where:

- `bindingQuality` is the registered normalized binding mean;
- `consensusQuality` is the consensus score from section 7;
- `candidateCoverage` is the authoritative singleton coverage from section 10;
- `completeness` is the observed required-method weight divided by expected required-method weight.

The frozen `mvp-v1.0` weights are `w_binding = 0.40`, `w_consensus = 0.30`, `w_coverage = 0.20`, and `w_completeness = 0.10`. When population coverage is disabled for an entire future approved profile, its weight is redistributed proportionally among enabled components and the effective weights are persisted. When enabled but missing for one candidate, do not redistribute; apply the missing-evidence penalty and a population warning.

### B-cell MVP profile

```text
scoreBeforePenalty =
    w_graphbepi * predictorMean
  + w_completeness * completeness

w_graphbepi + w_completeness = 1.0
```

For the MVP, `predictorMean` is the normalized GraphBepi fixture score. GraphBepi is a single fixture-backed method, so the B-cell track does not claim cross-predictor agreement or consensus. No HLA population-coverage value contributes to B-cell ranking. The frozen `mvp-v1.0` weights are `w_graphbepi = 0.90` and `w_completeness = 0.10`.

### Penalties

```text
missingEvidencePenalty = 0.10 * missingOptionalWeightFraction
softWarningPenalty = min(0.20, 0.05 * softWarningCount)
fixturePenalty = 0.00
finalScore = clamp01(scoreBeforePenalty - missingEvidencePenalty - softWarningPenalty)
```

Fixture provenance does not change a scientific score; it changes run quality and display status.

### Category defaults

- Hard failure: `REJECTED` regardless of score.
- `finalScore >= 0.75` and no blocking review condition: `RECOMMENDED`.
- `0.50 <= finalScore < 0.75`: `REVIEW`.
- `finalScore < 0.50`: `REJECTED` with `RANK-THRESHOLD-001`.

Thresholds are versioned and configurable.

### Stable sort

Sort by:

1. category order `RECOMMENDED`, `REVIEW`, `REJECTED`;
2. final score descending;
3. agreement descending;
4. completeness descending;
5. start ascending;
6. candidate key ascending.

Ranks are one-based within candidate track and category view.

## 13. Confidence label

Confidence describes evidence quality, not biological efficacy.

```text
HIGH:
  completeness == 1
  agreement >= 0.80
  no soft warnings except fixture provenance

MEDIUM:
  completeness >= 0.75
  agreement >= 0.60
  no hard failures

LOW:
  otherwise, provided the candidate is not hard-rejected
```

Rejected candidates have `confidence = NOT_APPLICABLE`.

## 14. Explanation generation

The deterministic explanation builder emits:

1. category and rank;
2. score components;
3. strongest supporting evidence;
4. warnings and failed rules;
5. provenance mix;
6. computational-only disclaimer.

An optional LLM may paraphrase this structure but must preserve numbers and rule IDs exactly. If post-generation validation fails, discard the LLM output and use the deterministic explanation.

## 15. Canonical replay

Replay input consists of:

- normalized sequence hash;
- immutable run configuration;
- ordered raw observations or exact connector cache keys;
- normalization registry version;
- rule profile version;
- ranking profile version.

A deterministic replay passes when canonical JSON of candidates, normalized evidence, rule outcomes, and rankings has the same SHA-256 as the stored replay hash. Timestamps and execution IDs are excluded.
